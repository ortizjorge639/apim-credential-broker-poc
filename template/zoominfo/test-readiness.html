Choose a test lane

Same endpoint. Different OAuth owner.

Start with this lane after common inputs are ready. Its main question is whether Foundry sends the invoking user's delegated ZoomInfo identity through APIM to Lookup.

Baseline / per-user identity

Foundry OAuth passthrough

Can test first

Foundry owns the delegated OAuth connection; APIM remains the governance/proxy layer.

  1. 1
    Configure Foundry OAuth connection

    Use the customer app details, approved scopes, and Foundry's matching registered callback. Put the secret only in the secure connection setup.

  2. 2
    Route through the APIM HTTPS endpoint

    Foundry must reach the registered HTTPS MCP address. The local mock at 127.0.0.1 is not reachable from hosted Foundry.

  3. 3
    Call only Lookup as test user

    Confirm delegated identity matches the signed-in test user; capture status, JSON-RPC result, and MCP isError.

PASS when That user's delegated authorization is proven and a successful, documented read-only Lookup returns through APIM.
Candidate / brokered token

APIM Credential Manager

Separate follow-on

APIM owns the OAuth connection and injects its backend token; test it separately from Foundry passthrough.

  1. 1
    Create a separate PKCE provider/connection

    Use the APIM Credential Manager portal's generic OAuth 2.0 with PKCE option and its APIM callback—not the Foundry callback.

  2. 2
    Prove mandatory S256 at runtime

    Observe code_challenge_method=S256; verify no-challenge authorization is rejected. Do not infer config from a guessed IaC property.

  3. 3
    Broker token and call Lookup

    Complete OAuth code exchange, then prove APIM's read-only Lookup succeeds and returns a valid MCP result.

PASS when S256, code exchange, and successful read-only Lookup are evidenced—not merely a connected status or token.

Important distinction: Customer ZoomInfo URLs/scopes are needed for both lanes. PKCE's portal-vs-IaC configuration question is separate: the portal option is documented, but the checked repo ARM/Bicep schema does not document a selector. This blocks guessing an automated field, not the Foundry test.

Decision rule

Run the local end-to-end simulations now to check OAuth→gateway→MCP wiring and token boundaries without customer inputs. For hosted Foundry, use customer inputs + reachable registered HTTPS MCP. Run APIM Credential Manager as a separate real-product lane; local S256 proves only the mock issuer/client flow.

What “complete” means

A token is not the finish line

Foundry lane evidence

Complete only after the actual Foundry-hosted call works as the intended person.

  • OAuth succeeds for the test user
  • Delegated identity is shown to be that user
  • HTTP success + no JSON-RPC error + MCP isError=false
  • Lookup behavior is verified read-only

APIM Credential Manager evidence

Complete only after the broker's exact PKCE behavior and end-to-end MCP call are proven.

  • APIM authorization uses S256; missing challenge is rejected
  • Authorization code exchanges with verifier
  • Successful read-only Lookup through APIM
  • Redacted evidence only; no token/body copied into repo

The immediate real-test dependency is customer ZoomInfo app + MCP information—not “APIM PKCE support.”

That customer information unlocks Foundry passthrough. APIM Credential Manager PKCE is an independent second experiment; its portal option is documented, while IaC selection and S256 enforcement still need specific proof.
