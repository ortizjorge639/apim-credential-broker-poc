# Customer replication runbook: ZoomInfo MCP with Foundry, Toolbox, and APIM

This runbook is a **planned, customer-environment procedure**, not a claim that the production integration has been deployed or validated. The local mock proves only synthetic protocol and architecture-shaped behavior. Run these steps only in a customer-approved non-production environment after the customer supplies the inputs below and approves the Azure resources, OAuth applications, costs, and test account.

For a shorter, portal-first walkthrough, start with [`portal-first-guide.md`](portal-first-guide.md). This runbook contains the detailed prerequisites, evidence rules, and safety gates.

## Scope and sequence

The current baseline is **Foundry → ZoomInfo**, using Foundry OAuth Identity Passthrough and ZoomInfo's Standard app with Authorization Code + PKCE. APIM is not in this baseline path. The proposed next experiment is **Foundry → APIM → Toolbox → ZoomInfo**, after the direct baseline succeeds. Measure APIM telemetry on that follow-on; do not assume what it will show. APIM Credential Manager is a separate optional experiment, not a prerequisite for either step.

| Stage | Path | Purpose and pass condition |
|---|---|---|---|
| 1. Baseline | Foundry → ZoomInfo | Verify the expected ZoomInfo/Okta sign-in, delegated test-user identity, and one successful read-only `Lookup`. No APIM claim is made. |
| 2. Proposed follow-on | Foundry → APIM → Toolbox → ZoomInfo | Verify the selected topology and token owner, call the same read-only `Lookup`, and inspect APIM telemetry. |
| Optional experiment | Foundry → APIM → ZoomInfo via Credential Manager | Separately evaluate APIM-owned OAuth and PKCE only if the team chooses this route. |

Do not interpret the local modes `foundry_oauth_passthrough` or `apim_credential_manager` as integrations with those Azure products. They are in-process simulations using synthetic tokens.

Enter secrets only in the customer's approved secret store or product connection UI.

## Important: what the current repository template does and does not deploy

`template/main.bicep`, `template/deploy.sh`, and `template/mcp-policy.xml` implement the existing Microsoft Graph `/me` APIM Credential Manager demonstration with a Foundry project-managed-identity caller. They are **not** a ready-to-deploy ZoomInfo passthrough stack:

- The policy calls Graph and retrieves an APIM Credential Manager token; it is not configured to forward a Foundry user's ZoomInfo bearer token.
- The sample validates one Foundry project managed identity, which proves caller gating, not delegated per-user identity. It binds one static Credential Manager authorization; dynamic per-user connection selection is not established by this sample.
- The Bicep OAuth provider is generic OAuth 2.0 without a documented IaC PKCE/S256 selector in the checked schema.
- The sample deploy script creates Azure resources and an Entra application/secret. Do not run it as a shortcut for this test.

The direct Foundry → ZoomInfo baseline does not need an APIM policy. The two files [`policy-foundry-passthrough.xml`](policy-foundry-passthrough.xml) and [`policy-apim-credential-manager.xml`](policy-apim-credential-manager.xml) are drafts with placeholders, not deployable policies. The Foundry draft assumes a signed ZoomInfo JWT with published OpenID metadata. The Credential Manager draft assumes an Entra JWT caller and one fixed connection accessed by APIM's managed identity; it does not prove per-user connection selection. Neither draft defines the proposed Toolbox route. Confirm every assumption against the customer design; only then create a route-specific policy and have the security/platform owner review its trust boundary, streaming behavior, caller authorization, backend restriction, tool allowlist, and secret-safe telemetry. Do not log Authorization headers, token-bearing query strings, or full Lookup payloads.

| [Foundry MCP authentication](https://learn.microsoft.com/azure/foundry/agents/how-to/mcp-authentication) and [MCP tool setup](https://learn.microsoft.com/azure/foundry/agents/how-to/tools/model-context-protocol) | Microsoft documents Foundry's MCP OAuth/Identity Passthrough setup. | That the specific ZoomInfo MCP service and customer's Standard app work with Foundry and produce the expected Okta SSO prompt. |
| APIM [expose an existing MCP server](https://learn.microsoft.com/azure/api-management/expose-existing-mcp-server) and [monitor MCP traffic](https://learn.microsoft.com/azure/api-management/monitor-mcp-servers) | Microsoft documents an external-MCP gateway pattern and default telemetry such as tool, client, duration, and success. Arguments/results are not included by default. | The proposed Toolbox endpoint, token ownership/propagation, identity, network path, and actual telemetry in the customer's route. |

These product references document component capabilities, not a completed ZoomInfo + Okta + Foundry + Toolbox + APIM deployment. This runbook is the project-specific integration procedure; it is not a vendor-certified end-to-end recipe.

Keep the permission boundary clear: **OAuth scopes define the data/API permissions on the token; the test scope defines which operation we choose to call.** A single read-only `Lookup` call does not prove the token can do only Lookup. Use only the provider-approved, least-privilege OAuth scopes; restrict the exposed tool list and test arguments independently.

## Phase 1 — preflight the customer inputs

1. Gather the approved configuration inputs from the customer owners. The portal walkthrough does not require copying `config.example.json`, running Bicep, or running a deployment script. If the team chooses to use the optional offline validator, keep its config in an approved customer-controlled location outside the repository and never include `client_secret` or tokens.
2. Confirm `app_type` is `Standard`, the ZoomInfo app is configured for Authorization Code + PKCE, the `authorization_mode` is `foundry_oauth_passthrough`, endpoint URLs use HTTPS, and scopes exactly match the approved ZoomInfo registration. The supplied screen lists `zi_api zi_mcp api:data:mcp offline_access`; get ZoomInfo's written confirmation of what the ZoomInfo-specific scopes grant and whether all are required. Do not assume the public scope catalog defines them or switch to Client Credentials for the per-user delegated test.
3. Confirm the customer has documented `Lookup` as read-only and supplied only safe non-sensitive test arguments. The local config check restricts the tool name; it cannot validate ZoomInfo's actual semantics.
4. (Optional) If the team wants a local structural check of its recorded config, run the offline preflight from the repository root:

   ```sh
   python -B template/zoominfo/zoominfo_validation.py --config path/to/customer-config.json
   ```

   This validator is optional and is not part of the portal procedure. `READY_FOR_CUSTOMER_INPUT` means only that the local fields are complete and structurally valid. It makes no network call and is not a runtime pass.

5. Before the direct baseline, have the customer approve the target URL, callback, requested scopes, test identity/query, logging/redaction, budget, and cleanup plan. Review an APIM policy only before the separate Toolbox/APIM follow-on or Credential Manager experiment. Obtain the customer's explicit approval before creating/updating any cloud resources or app registrations.

## Phase 2 — run the direct Foundry baseline

6. In Foundry, create a per-user OAuth Identity Passthrough connection to the customer-approved ZoomInfo MCP endpoint. Use the Standard app's Authorization Code + PKCE settings and exact approved scopes.
7. Select **Connect**. Copy the redirect URI that Foundry displays. Ask the identity owner to register that exact URI on the ZoomInfo app. Keep the client secret only in the approved Foundry connection configuration.
8. Save the MCP connection. Sign in as the named test user and consent only to approved scopes. A connected status is setup evidence, not a test pass.
9. In the Foundry Playground, confirm the available tools. Call only the documented, read-only `Lookup` tool with the approved safe arguments. Do not call write, update, or delete tools.
10. Capture a redacted timestamp, Foundry connection/tool name, HTTP status, JSON-RPC error status, MCP `isError`, and evidence that ZoomInfo received the intended user's delegated identity. Confirm that the ZoomInfo/Okta login prompt matches the expected SSO flow.
11. Report **GO** only if the hosted call succeeds, `Lookup` is confirmed read-only, and the user identity is verified. Otherwise report **PARTIAL** or **STOP**. This direct test does not test APIM or APIM telemetry.

## Phase 3 — proposed Toolbox through APIM follow-on

Proceed only after the direct baseline is recorded and the owners approve this follow-on.

12. Ask the Toolbox owner to document the hosting location, exposed MCP endpoint, ZoomInfo authentication method, token/identity owner, and expected telemetry. Do not infer these details from the term “Toolbox.”
13. In the APIM portal, confirm the approved instance is provisioned, supports MCP, and can reach the Toolbox endpoint. Create an MCP server from the existing Toolbox endpoint using its documented transport.
14. In the APIM MCP server's **Tools** blade, expose only the approved read-only `Lookup` capability and required MCP protocol methods.
15. Have the platform/security owner define and review APIM caller authentication, backend authentication, routing, tool allowlist, streaming, and secret-safe telemetry. Do not paste the Graph example policy or either ZoomInfo draft policy without adapting and reviewing it.
16. Connect a separate Foundry test agent to the APIM MCP endpoint with the agreed caller-authentication mode. Run the same approved `Lookup` query.
17. Record whether the call succeeds, which identity ZoomInfo receives, and what APIM telemetry shows for tool name, client, duration, status, and errors. Microsoft's documented default telemetry excludes tool arguments and results. Compare this with the direct baseline. Treat payload logging as a separate, explicitly approved data-exposure and retention decision.
18. Do not claim per-user success unless the user's identity is verified through Toolbox to ZoomInfo. Do not claim telemetry benefits until they are observed.

**Telemetry reference:** [Monitor MCP server traffic in APIM](https://learn.microsoft.com/azure/api-management/monitor-mcp-servers) documents default request rows and MCP dimensions such as operation, tool name, client, duration, and success. Tool arguments/results are not included by default; enabling payload logging can expose sensitive data. This is a first-party precedent for APIM observing an MCP route, not proof that a particular Toolbox topology or identity claim has been validated.

## Optional separate experiment — APIM Credential Manager

This is not the direct Foundry baseline or the proposed Toolbox route. Run it only if the team separately chooses APIM to own the ZoomInfo OAuth connection.

1. Create a separate Generic OAuth 2.0 with PKCE provider/connection in APIM and register its APIM callback with the ZoomInfo app owner.
2. Inspect the actual authorization request in browser Developer Tools. Record only whether `code_challenge` is present and whether `code_challenge_method=S256`. Never save OAuth values or export a HAR containing them.
3. If the customer approves it, test whether ZoomInfo rejects a no-challenge authorization request. Do not sign in or consent if the request proceeds.
4. Run `Lookup` through a reviewed APIM route. Verify the connection identity model. A fixed/shared connection is not per-user evidence.
5. If S256, identity, or Lookup is not proven, record **PARTIAL/BLOCKED**. The checked IaC contract does not document a setting that selects mandatory PKCE S256; do not invent one.

## Phase 4 — record and clean up

19. Record each route's observed outcome in the customer's approved evidence system. The JSON example and validator are optional references; do not copy customer URLs, token material, or full response bodies into this repository.
20. (Optional) If the team uses the local evidence validator, set `authorization_mode` accurately in the customer config and run:

   ```sh
   python -B template/zoominfo/zoominfo_validation.py \
     --config path/to/customer-config.json \
     --evidence path/to/redacted-evidence.json \
     --out path/to/customer-result.json
   ```

21. Interpret `GO` only for the specific route that produced the evidence. The tool cannot independently validate evidence or prove ZoomInfo entitlements; the customer test owner must review it.
22. Store signed-off evidence in the customer's approved location. Do not check customer endpoint URLs, scopes, test identities, or evidence into this repository without explicit review and approval.
23. Revoke test-user consent and remove temporary Foundry connections/agents and any approved APIM/Toolbox resources under the customer's cleanup process. Record cleanup in the customer system of record.

## Stop, rollback, and cleanup

- Stop on unclear consent, unexpected scopes, identity mismatch, unapproved data access, non-read-only tool behavior, token leakage, TLS/network/authentication failures, or a non-MCP response. Preserve only redacted diagnostic metadata and involve the customer's security/platform owner.
- Revoke test-user consent/authorization and remove the temporary Foundry connection/agent and APIM connection/policies/resources according to the customer's approved change/retention process. Confirm no active test credentials or public ingress remain. Do not delete a shared RG, app, APIM service, or customer resource unless its exact ownership/scope is verified and the customer explicitly approves deletion.
- Record cleanup owner, date, resource identifiers in the customer system of record (not the repository), and whether any approved test credential rotation/revocation is needed.

## Confidence statement and known boundary

The repository contains a local OAuth/MCP mock and Foundry-like/APIM-like simulation. It tests synthetic PKCE, token separation, a read-only tool allowlist, and mock Lookup. It does **not** run hosted Foundry, APIM, Credential Manager, or ZoomInfo. A local `PASS` is not customer-environment evidence. The direct test must validate the real Foundry-to-ZoomInfo delegated path. The follow-on must validate the chosen Toolbox/APIM topology and actual telemetry.
